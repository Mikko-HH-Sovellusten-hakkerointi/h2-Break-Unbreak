### OWASP: OWASP Top 10: A01 Broken Access Control

- Broken Access Control on yksi yleisimmistä ja vakavimmista sovellusvioista: lähes kaikki sovellukset altistuvat sille, ja tapauksia on valtavasti.
- Perusongelma on se, että käyttäjä pääsee tekemään tai näkemään asioita, joihin hänellä ei pitäisi olla oikeuksia.
  - Seurauksena tietovuotoja, tietojen muuttamista tai oikeuksien korottamista ilman lupaa.
- Esimerkkeinä mm. URL‑osoitteen tai parametrien muokkaus, toisten käyttäjien tietojen katselu (IDOR), puutteellisesti suojatut API‑kutsut yms.
- Voidaan ehkäistä sillä, että oletusarvoisesti kaikki pääsy on estetty, tarkistukset palvelimella, oikeuksien keskitetty käsittely ja kunnollinen testaus.

### Karvinen 2023: Find Hidden Web Directories - Fuzz URLs with ffuf

- Web-sivustoilla voi olla piilotettuja hakemistoja, joita ei näy normaalissa selaamisessa (/admin, .svn yms.), mutta jotka voidaan silti löytää kokeilemalla eri URL-polkuja.
- Ffuf on työkalu, jolla voidaan automaattisesti kokeilla paljon eri URL-polkuja sanalistan avulla ja löytää tällaisia piilotettuja sivuja.
  - Testaamista harjoitellaan paikallisella esimerkkipalvelimella, jotta toiminta on turvallista ja laillista.
- Kaikki vastaukset eivät ole oikeita osumia, joten tuloksia pitää suodattaa (esim. vasteen koon tai sanamäärän perusteella)
  - Oikeat osumat erottuvat usein poikkeavana vasteena, ja ne kannattaa varmistaa selaimella tai curlilla.

- Oma huomio: Ffuf on tehokas työkalu, mutta testaajan tehtävä on ymmärtää sen antamia tuloksia ja tarkistaa ne itse, ettei tule ns. false positiveja.

### PortSwigger: Access control vulnerabilities and privilege escalation

- Broken access control tarkoittaa sitä, että käyttäjä voi tehdä asioita tai nähdä tietoja, joihin hänellä ei ole oikeutta.
- Merkittävimpiä riskejä ovat
  	- Toisen käyttäjän tietojen katselu tai muokkaus.
	- Ylläpitäjän oikeuksien saaminen ilman lupaa.
	- API-rajapintojen käyttö ilman asianmukaisia käyttöoikeuksia.
 - Näitä voidaan ehkäistä
	- Tarkistamalla käyttöoikeudet aina palvelinpuolella.
 	- Myöntämällä käyttäjille vain välttämättömät oikeudet (least privilege).
  	- Estämällä pääsyn oletuksena ja sallimalla vain tarvittavat toiminnot.

Lyötyäni tovin päätäni seinään, huomasin ottaneeni ehkä turhan kirjaimellisesti tehtävässä olevan rajoituksen, jossa lähdekoodia ei saa tutkia ennen tehtävän ratkaisua. Jotenkin sunnuntaikoomassa luulin tämän tarkoittavan myös selaimen kautta tutkittavaa lähdekoodia. 
Nyt jälkiviisaana se on helppo sanoa, että olisihan se melko hupsua, jos ei selaimen työkaluja voisi käyttää, koska sitähän hakkeritkin tekevät - joten päätin ottaa nämä käyttöön.
Tutkin siis hieman sivuston lähdekoodia Firefoxin Web Developer Toolsin avulla ja huomioni kiinnittyi kentän input typeen, joka oli **number**. Muutin kentän selaimessa tavalliseksi tekstikentäksi, minkä jälkeen siihen pystyi syöttämään myös muuta sisältöä kuin numeroita.

Tässä jälleen tärkeä opetus web-sovellusten tietoturvasta: pelkät selaimessa olevat syöterajoitukset eivät yksinään riitä suojaamaan mitään. Käyttäjä voi muokata sivun rakennetta omassa selaimessaan, joten palvelin ei voi luottaa siihen, että sille lähetetään vain käyttöliittymän sallimaa dataa. Tämän vuoksi tarkistukset täytyy tehdä myös palvelimen puolella.

että kyselyn toimintaa pystyi muuttamaan käyttäjän syötteellä ja sovellus oli haavoittuvainen SQL-injektiolle.

Ensimmäisen onnistuneen injektion jälkeen kokeilin erilaisia tapoja selvittää tietokannan rakennetta. En tehtävänannon mukaisesti lähtenyt tutkimaan etukäteen muuta lähdekoodia tai tietokannan sisältöä enkä selvittämään, millaisia rivejä sinne oli tallennettu. Lisäsin **foo' OR '1'='1' ORDER BY password** -injektion, koska oletin sovelluksen näyttävän vain ensimmäisen kyselyn palauttaman rivin, sillä SQL:n ORDER BY-lausekkeen tarkoituksena on järjestää kyselyn tulokset valitun sarakkeen perusteella (Portswigger). 
Muuttamalla tulosten järjestystä pyrin selvittämään, voisiko jokin muu tietokannan rivi nousta ensimmäiseksi.

Tässä tapauksessa aakkosjärjestys nosti ylläpitäjän salasanan ensimmäiseksi tulokseksi, jolloin salasana paljastui. Eli käytännössä onnistuin hieman yllättäen löytämään lipun jo tässä vaiheessa, vaikka tarkoitukseni oli alun perin vain selvittää paremmin kyselyn toimintaa.

from flask import Flask, render_template, request # sudo apt-get install python3-flask

app.config['SQLALCHEMY_DATABASE_URI'] = 'sqlite:///:memory:'

@app.route("/", methods=['POST', 'GET'])

		pin = str(request.form['pin'])
	else:

	row = ""
	with app.app_context():

def runSql(sql):
	with app.app_context():
		res=db.session.execute(text(sql))
		db.session.commit()

<br>

Koodia tutkittuani tulin siihen tulokseen, että kriittisin haavoittuvuus on tässä:

**Rivi 22:** 

```bash
sql = "SELECT password FROM pins WHERE pin='"+pin+"';"
```
**Rivi 25:**

```bash
res=db.session.execute(text(sql))
```

<br>

Eli käyttäjän syöte liitettiin suoraan SQL-kyselyn sekaan. Jos käyttäjä kirjoitti jotain SQL-koodia sisältävää, tietokanta saattoi tulkita sen osaksi kyselyä. Tämä haavoittuvuus korjattiin käyttämällä parametrisoitua SQL-kyselyä. Kyselyssä **'"+pin+"';"** korvattiin paikkamerkillä **:pin**. Se kertoo tietokannalle, että tähän kohtaan tulee myöhemmin jokin arvo:

<br>

**Rivi 22:**

```bash
sql = text("SELECT password FROM pins WHERE pin=:pin")
```
<br>

Tässä taas annetaan paikkamerkille varsinainen arvo käyttäjän syötteestä:

<br>

**Rivi 25:**

```bash
res = db.session.execute(sql, {"pin": pin})
```
<br>

Yhdessä nämä tekevät sen, että syöte ja SQL-kysely pidetään erillään toisistaan - eli käyttäjän syötettä käsitellään pelkkänä datana eikä osana SQL-koodia, minkä pitäisi estää SQL-injektion onnistumisen.

## e) Fix the 020-your-eyes-only vulnerability

Tätä tehtävää varten minun oli käyttää VS Codea, sillä ilman sitä Python-tiedostojen selailu olisi ollut melko työlästä. Lopulta haavoittuvuus löytyi views.py-tiedostosta polulta ./challenges/020-your-eyes-only/logtin/hats/views.py. 

AdminShowAllView salli aiemmin pääsyn kaikille kirjautuneille käyttäjille, mutta korjaus lisäsi admin-oikeuksien tarkistuksen myös tähän näkymään-näkymään, kun koodin perään lisätään vielä:

```bash
and self.request.user.is_staff 
```

Eli käytännössä tämä on ns. authorization fix, joka estää tavallisia käyttäjiä näkemästä admin-sivun sisältöä.
